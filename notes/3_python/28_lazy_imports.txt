28  --  lazy / local imports: import inside a function and when to use it

1)  What a lazy import is

A "lazy" or "local" import is an  import  statement written INSIDE a function body instead of at the top of the file. The import only runs when that function is actually called, not when the file is first loaded.

     import json

     def read_config(path):
         import yaml
         with open(path) as fh:
             return yaml.safe_load(fh)

Here  json  is a top-level import and loads immediately when the file is imported.  yaml  is a local import and only loads the first time  read_config  is actually called. If nobody ever calls  read_config , the yaml module never loads at all.

2)  How it differs from a top-level import

  -  TOP-LEVEL import: runs ONCE, at the moment Python first loads the file. Every function in the file can see the imported name from that point on.

  -  LOCAL import: runs EVERY time the function is called, but Python caches loaded modules internally. So the first call actually loads the module; every later call just looks up an already-loaded module in memory.

The end effect: local imports move the cost of importing from file-load time to function-call time, and only for the first call.

3)  Why we do it

Three real reasons. If none of these apply, keep the import at the top  --  that is the default.

  (a)  BREAK A CIRCULAR IMPORT

       A CIRCULAR IMPORT is two files that each import the other, so neither can finish loading. Moving one of the two imports INSIDE a function delays it until after both files have finished loading, which breaks the cycle.

  (b)  OPTIONAL OR HEAVY DEPENDENCY

       Some libraries are big and slow to load, or are only needed for one specific feature. Loading them at the top slows down every program start-up, even when the feature is not used. Putting the import inside the feature's function means you only pay that cost when the feature actually runs.

  (c)  CONDITIONAL / RUNTIME-DECIDED IMPORT

       When you need to import DIFFERENT modules based on a runtime flag (a CLI argument, an environment variable, a config value), a local import inside an  if  branch is the cleanest way. Only one of the branches runs, so only one of the modules loads.

4)  A concrete example for each reason

Reason (a)  --  breaking a circular import. In  user.py  the import is local, not top-level:

     def get_admin():
         from orders import last_order
         return last_order()

And in  orders.py  a top-level import is fine:

     from user import get_admin

If  user.py  put  from orders import last_order  at the top and  orders.py  put  from user import get_admin  at the top, both files would try to finish loading each other at the same time and Python would fail. Moving one to a local import fixes the cycle.

Reason (b)  --  heavy optional dependency. matplotlib is large, so it loads only when actually plotting:

     def make_plot(points):
         import matplotlib.pyplot as plt
         plt.plot(points)
         plt.show()

If the program never calls  make_plot , matplotlib never loads and startup stays fast.

Reason (c)  --  runtime-decided import:

     def get_driver(use_simulator):
         if use_simulator:
             from drivers.simulator import SimDriver
             return SimDriver()
         else:
             from drivers.hardware import HardwareDriver
             return HardwareDriver()

Only the branch that runs loads its module. If the user picked the simulator, the real-hardware driver code is never even imported.

5)  Downsides to know

  -  HIDDEN DEPENDENCIES. Reading the top of the file no longer shows everything the file depends on. You have to scan every function too. This makes the file harder to understand at a glance.

  -  LATE FAILURE. A missing library will not fail at program start-up; it will fail only when the function is first called. That could be minutes into a running program, which is a worse debugging experience than a clear failure at import time.

  -  SLIGHT RUNTIME COST. Every time the function runs, Python re-reads the import line. The FIRST call loads the module (real work). Every call after that is very fast, because Python already has the module in memory and just looks it up by name. You never notice this cost at ordinary call rates. But if the function runs millions of times inside a fast loop, even that tiny lookup adds up  --  in that case, move the import to the top of the file.

6)  Common mistakes

  -  Using a local import for NO reason. If the module is cheap to load, always used, and there is no circular problem, put it at the top. Local imports should be a deliberate choice, not a habit.

  -  Putting a local import inside a hot loop that runs millions of times per second. The lookup is fast but not free. Move it out of the loop, or up to a top-level import.

  -  Forgetting to actually write the  import  line inside the function and relying on a top-level name that is not there. This gives a  NameError  at call time instead of at file-load time. Harder to trace.
