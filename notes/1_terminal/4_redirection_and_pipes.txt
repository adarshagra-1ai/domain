4  --  Output redirection and pipes

1)  echo  --  print text to the screen

The command  echo  prints whatever text you give it, then moves to a new line.

Syntax:

     echo  <text>

Example:

     adarsh@laptop:~$  echo hello
     hello

     adarsh@laptop:~$  echo hello world
     hello world

On its own  echo  looks pointless  --  you already know what you typed. It earns its place once its output is sent somewhere other than the screen.

2)  echo and spaces  --  why quotes matter

The shell splits your line into pieces at every space. It hands  echo  a LIST of words, and  echo  joins them back with exactly ONE space between each.

So extra spaces disappear:

     adarsh@laptop:~$  echo hello        world
     hello world

Wrap the text in quotes and it arrives as ONE piece, spaces and all:

     adarsh@laptop:~$  echo "hello        world"
     hello        world

3)  Single quotes vs double quotes

Both  " ... "  and  ' ... '  keep the text together. The difference is how much the shell is still allowed to change inside them.

  -  SINGLE quotes  ' ... '   ->  everything inside stays exactly as typed.
  -  DOUBLE quotes  " ... "   ->  the shell still replaces a few special things, such as a  $name  variable.

Concrete case:  $HOME  is a shell variable holding the path of your home folder.

     adarsh@laptop:~$  echo "$HOME"
     /home/adarsh

     adarsh@laptop:~$  echo '$HOME'
     $HOME

The other everyday use of the two forms is NESTING  --  putting one kind of quote inside the other:

     adarsh@laptop:~$  echo 'print("hello")'
     print("hello")

     adarsh@laptop:~$  echo "it's fine"
     it's fine

Rule of thumb:

     Text with  $  that must stay literal   ->  single quotes
     Text containing double quotes          ->  single quotes
     Text containing single quotes          ->  double quotes

4)  >  --  send a command's output into a file

The  >  symbol REDIRECTS a command's normal output away from the terminal and into a file.

     command  >  filename

Example:

     adarsh@laptop:~$  echo hello > greeting.txt

Nothing appears on screen  --  the text went into the file instead. Check it with  cat :

     adarsh@laptop:~$  cat greeting.txt
     hello

5)  Any command's output, not just echo

     adarsh@laptop:~$  ls > list.txt

     adarsh@laptop:~$  cat list.txt
     Documents
     Downloads
     Music
     greeting.txt
     list.txt

Two things to notice:

  -  The names come out one per line, not side by side. When  ls  sees that its output is going to a file instead of a terminal, it switches to one-name-per-line.
  -  list.txt  lists itself. The shell creates the empty file FIRST, then runs  ls .

6)  >  OVERWRITES  --  the danger

If the file already exists,  >  empties it first, then writes the new output. The old contents are gone. No warning, no undo.

     adarsh@laptop:~$  echo "first line" > notes.txt
     adarsh@laptop:~$  cat notes.txt
     first line

     adarsh@laptop:~$  echo "second line" > notes.txt
     adarsh@laptop:~$  cat notes.txt
     second line

"first line" is not sitting above it. It was deleted.

     WARNING:  never point  >  at a file you care about. Like  rm , this is instant and permanent.

7)  >>  --  APPEND instead of overwrite

Two right-angle brackets add to the END of the file and keep what was already there.

     adarsh@laptop:~$  echo "first line" > notes.txt
     adarsh@laptop:~$  echo "second line" >> notes.txt
     adarsh@laptop:~$  echo "third line" >> notes.txt

     adarsh@laptop:~$  cat notes.txt
     first line
     second line
     third line

If the file does not exist yet,  >>  creates it, exactly like  > . The difference shows up only when the file already has content.

8)  >  vs  >>  side by side

     >    file does not exist   ->  create it, write the output
     >    file exists           ->  ERASE it, write the output
     >>   file does not exist   ->  create it, write the output
     >>   file exists           ->  keep it, add the output at the end

Rule of thumb:

     Fresh file every time      ->  >
     Growing log, adding on     ->  >>

9)  >  does not catch error messages

A command's error messages travel separately from its normal output, and  >  catches only the normal output.

     adarsh@laptop:~$  ls missing_folder > out.txt
     ls: cannot access 'missing_folder': No such file or directory

     adarsh@laptop:~$  cat out.txt
     adarsh@laptop:~$

The error still printed on screen.  out.txt  was created but is EMPTY, because the command produced no normal output at all.

Notice that the file was created at all. The shell prepares the file before the command even runs, so the existence of a file is never proof that the command worked. Check the contents.

10)  The sample file used from here on

Everything so far has been about WHERE output goes. The next four commands are the other half: each one takes text IN, does one small job on it, and prints the result.

Every example below reads the same file:

     adarsh@laptop:~$  cat fruits.txt
     banana
     apple
     cherry
     apple
     date

11)  head  --  the first lines of a file

By default  head  prints the first 10 lines. Our file has only 5, so all of them print:

     adarsh@laptop:~$  head fruits.txt
     banana
     apple
     cherry
     apple
     date

Choose how many with  -n :

     adarsh@laptop:~$  head -n 3 fruits.txt
     banana
     apple
     cherry

Use it to peek at the top of a large file instead of dumping the whole thing with  cat .

12)  tail  --  the last lines of a file

Mirror image of  head . Default is the last 10 lines;  -n  chooses how many.

     adarsh@laptop:~$  tail -n 2 fruits.txt
     apple
     date

One extra flag is worth knowing now:  -f  ("follow") keeps the command running and prints new lines as they get added to the file. This is how people watch a log file live:

     adarsh@laptop:~$  tail -f /var/log/syslog

Press  Ctrl + C  to stop following and return to the prompt.

13)  wc  --  count lines, words and characters

     adarsh@laptop:~$  wc fruits.txt
     5  5  31  fruits.txt

Three numbers, always in this order:

     5    ->  LINES
     5    ->  WORDS
     31   ->  CHARACTERS (newline characters included)

Ask for one number only with a flag:

     adarsh@laptop:~$  wc -l fruits.txt
     5 fruits.txt

     adarsh@laptop:~$  wc -w fruits.txt
     5 fruits.txt

     adarsh@laptop:~$  wc -c fruits.txt
     31 fruits.txt

wc -l  is the one you will type most  --  "how many lines is this?"

14)  sort  --  put lines in order

Prints the lines in alphabetical order. THE FILE ITSELF IS NOT CHANGED  --  sort  only prints a sorted copy.

     adarsh@laptop:~$  sort fruits.txt
     apple
     apple
     banana
     cherry
     date

     adarsh@laptop:~$  cat fruits.txt
     banana
     apple
     cherry
     apple
     date

Two useful flags:

  -  -r   REVERSE order

        adarsh@laptop:~$  sort -r fruits.txt
        date
        cherry
        banana
        apple
        apple

  -  -n   NUMERIC order. Without it,  sort  compares text character by character, so  10  lands before  9  (the character "1" comes before "9").

        adarsh@laptop:~$  cat numbers.txt
        10
        9
        100

        adarsh@laptop:~$  sort numbers.txt
        10
        100
        9

        adarsh@laptop:~$  sort -n numbers.txt
        9
        10
        100

Each of these commands can take a FILE NAME as an argument:

     wc -l fruits.txt

If you leave the file name OUT, the command waits for text to be handed to it from somewhere else:

     adarsh@laptop:~$  wc -l

It just sits there, because nothing is feeding it. Press  Ctrl + C  to get out.

15)  What a pipe does

The  |  symbol is called a PIPE. It takes the normal output of the command on its LEFT and feeds it in as the input of the command on its RIGHT.

     command A  |  command B

     command A  --->  its output  --->  command B  --->  terminal window

Nothing is written to disk. The text goes straight from one program into the next.

Three rules follow from that:

  -  The command on the RIGHT must be one that reads text input. The  head / tail / wc / sort / cat  family does;  mkdir  does not, because it expects a folder name as an argument.

        adarsh@laptop:~$  ls | mkdir
        mkdir: missing operand

  -  Only normal output travels through a pipe. Error messages go straight to your screen and skip the pipe entirely, so the command on the right receives nothing.

        adarsh@laptop:~$  ls missing_folder | wc -l
        ls: cannot access 'missing_folder': No such file or directory
        0

16)  First example  --  count your files

     adarsh@laptop:~$  ls
     Documents  Downloads  Music  fruits.txt

     adarsh@laptop:~$  ls | wc -l
     4

Step by step:

     1)  ls  produces four names, one per line, as its output.
     2)  The pipe hands those four lines to  wc -l  instead of to the screen.
     3)  wc -l  counts them and prints  4 .

Notice that  wc -l  got NO file name here. It counted whatever the pipe fed it.

17)  Sorting, then trimming

     adarsh@laptop:~$  sort fruits.txt | head -n 2
     apple
     apple

sort  produced five lines in order;  head -n 2  kept the first two.

Swap the two commands and the meaning changes completely:

     adarsh@laptop:~$  head -n 2 fruits.txt | sort
     apple
     banana

Now  head  took the first two lines of the FILE ( banana  and  apple ), and  sort  ordered just those two. Read a pipeline left to right: each step only ever sees what the previous step handed over.

18)  Chaining more than two commands

There is no limit. Each  |  passes the result along.

     adarsh@laptop:~$  sort fruits.txt | head -n 3 | wc -l
     3

     1)  sort         ->  five lines in order
     2)  head -n 3    ->  the first three of them
     3)  wc -l        ->  counts those three  ->  3

19)  Pipe or redirect?  --  they are not the same

     >    sends output to a FILE      (the output stops there, on disk)
     |    sends output to a COMMAND   (the output keeps travelling)

Use both in one line  --  pipe through the commands you need, then redirect the final result into a file:

     adarsh@laptop:~$  sort fruits.txt | head -n 3 > top3.txt

     adarsh@laptop:~$  cat top3.txt
     apple
     apple
     banana

The  >  applies to the LAST command in the chain, not to the whole line.
