1  --  HTTP idea  (request, response,
         method, status)

1)  What HTTP is

HTTP (HyperText Transfer Protocol) is the
plain-text messaging rulebook that browsers,
mobile apps, and command-line tools use to
talk to servers on the web.

Facts you need for now:

  -  Every time you open a web page, click
     a link, or an app fetches data, HTTP
     is doing the work under the hood.
  -  HTTP is a TEXT-based protocol: the
     messages are readable strings, not
     binary.
  -  The version most sites use today is
     HTTP/1.1 or HTTP/2. From a beginner's
     view they behave the same way.


2)  Client-server model

HTTP is strictly ONE-WAY:

     CLIENT           --request-->      SERVER
     (browser,                          (a program
     mobile app,                        listening on
     curl, ...)                         port 80/443)

     CLIENT           <--response--     SERVER

Rules:

  -  The client always ASKS FIRST.
  -  The server responds to that one
     request and then stops.
  -  Each request is INDEPENDENT (HTTP is
     stateless by design; cookies and
     tokens add state on top).


3)  Anatomy of an HTTP request

A raw request has 4 parts:

     1. request line   ->  method + path +
                           protocol
     2. headers        ->  key: value lines
     3. blank line     ->  separator
     4. body           ->  optional (mainly
                           for POST / PUT /
                           PATCH)

Example raw request:

     GET /users/42 HTTP/1.1
     Host: api.example.com
     Accept: application/json
     User-Agent: curl/8.0.1


Breakdown:

  -  GET                 the METHOD (what
                         to do)
  -  /users/42           the PATH (which
                         resource)
  -  HTTP/1.1            the protocol
                         version
  -  Host: ...           required header
                         saying which
                         server this is for
  -  Accept: ...         header saying what
                         response format
                         the client wants


4)  Anatomy of an HTTP response

A raw response has 3 parts:

     1. status line  ->  protocol + status
                         code + reason phrase
     2. headers      ->  key: value lines
     3. blank line   ->  separator
     4. body         ->  the actual data
                         (HTML, JSON, image
                         bytes, ...)

Example raw response:

     HTTP/1.1 200 OK
     Content-Type: application/json
     Content-Length: 29

     {"id": 42, "name": "Adarsh"}

Breakdown:

  -  HTTP/1.1                the protocol
  -  200                     the STATUS
                             CODE (see
                             section 6)
  -  OK                      short reason
                             phrase
  -  Content-Type: ...       what kind of
                             data is in
                             the body
  -  Content-Length: ...     how many bytes
  -  {...}                   the body


5)  HTTP methods  (what the request wants
    to do)

The METHOD is the VERB of the request.
Each one has a conventional meaning.

     GET       READ. Fetch a resource.
               Should not change anything
               on the server. Usually no
               body.

     POST      CREATE. Add a new resource,
               or submit form data. Body
               carries the new content.

     PUT       REPLACE. Overwrite a resource
               with the given full content.

     PATCH     PARTIAL UPDATE. Change only
               the fields you send.

     DELETE    REMOVE. Delete the resource.

     HEAD      Like GET, but response has
               no body (only headers).
               Useful for checking if a
               resource exists.

     OPTIONS   Ask what methods and headers
               are allowed. Used by
               browsers for CORS
               pre-flight.

Rule of thumb:  GET should never change
data on the server. Use POST / PUT /
PATCH / DELETE for changes.


6)  Status codes  (what the response says
    happened)

Every response has a 3-digit STATUS CODE.
The FIRST digit tells you the family.

     1xx   informational. Rare in practice.

     2xx   SUCCESS.
             200   OK             standard
                                  success
             201   Created        a new
                                  resource
                                  was created
             204   No Content     success,
                                  but no
                                  body

     3xx   REDIRECT.
             301   Moved Permanently
             302   Found (temporary
                         redirect)
             304   Not Modified   cached
                                  version is
                                  still fresh

     4xx   CLIENT error (your request is
                         wrong).
             400   Bad Request    malformed
                                  input
             401   Unauthorized   no valid
                                  auth
                                  credentials
             403   Forbidden      auth is
                                  valid but
                                  not allowed
             404   Not Found      resource
                                  does not
                                  exist
             405   Method Not Allowed
             409   Conflict       state clash
             422   Unprocessable
                   Entity         validation
                                  failed
             429   Too Many Requests

     5xx   SERVER error (the server broke).
             500   Internal Server Error
             502   Bad Gateway    upstream
                                  server
                                  problem
             503   Service Unavailable
             504   Gateway Timeout


7)  Headers  (metadata about the message)

Headers are  key: value  lines, one per
line, in both requests and responses.


Common request headers:

     Host: api.example.com
     Accept: application/json
     User-Agent: curl/8.0.1
     Authorization: Bearer eyJhbGciOi...
     Content-Type: application/json


Common response headers:

     Content-Type: application/json
     Content-Length: 29
     Cache-Control: no-store
     Set-Cookie: session=abc; Path=/


Header names are case-insensitive but
usually written as  Title-Case  with
hyphens.


8)  Body  (the actual payload)

The BODY is optional. It carries data:

  -  REQUESTS: mostly on POST, PUT, PATCH.
     Usually JSON (JavaScript Object
     Notation) for APIs; sometimes form
     data or file uploads.

  -  RESPONSES: HTML for web pages, JSON
     for APIs (Application Programming
     Interfaces), image bytes for images,
     etc.

The  Content-Type  header tells the other
side how to read the body:

     application/json          a JSON string
     application/x-www-        classic HTML
       form-urlencoded         form data
     multipart/form-data       file upload
     text/html                 an HTML page
     text/plain                plain text


9)  Try it with curl

curl  is a command-line tool for making
HTTP requests. It comes pre-installed on
most Linux systems.


Simple GET:

     curl https://example.com

Prints the response body (an HTML page) to
your terminal.


See headers AND body with  -i :

     curl -i https://example.com

Now the status line and all response
headers appear at the top of the output.


See ONLY the response headers with  -I :

     curl -I https://example.com

Output (excerpt):

     HTTP/1.1 200 OK
     Content-Type: text/html; charset=UTF-8
     Content-Length: 1256
     Date: ...

The  HTTP/1.1 200 OK  is the status line
from section 4.


POST with a JSON body:

     curl -X POST \
          -H "Content-Type: application/json" \
          -d '{"name": "adarsh"}' \
          https://httpbin.org/post

     -X POST                       set the
                                   method
     -H "..."                      set a
                                   header
     -d '...'                      set the
                                   body
     https://httpbin.org/post      the URL

Every  curl  option maps to one of the
concepts from sections 3 to 8.


10)  Common gotchas

  (a)   Wrong method for the action

        Using GET to CREATE data (with a
        query string carrying the payload)
        is a common mistake. GET is for
        READING. Use POST / PUT / PATCH /
        DELETE for changes so that
        proxies, caches, and search
        engines do not accidentally
        trigger the action.


  (b)   404 vs 500

        404  =  the URL you asked for does
                not exist on the server.
                Fix: check the path.

        500  =  the URL exists but the
                server code crashed while
                handling it. Fix: server
                logs, not client input.


  (c)   Missing Content-Type on POST

        If you POST a JSON body but do
        not send  Content-Type:
        application/json  , many servers
        will read the body as plain text
        and fail to parse it. Add the
        header explicitly.


  (d)   Case in header VALUES

        Header NAMES are case-insensitive
        ( Content-Type  =  content-type ),
        but header VALUES are not (a
        Bearer token or a URL inside a
        header is exact).
