from __future__ import annotations   and modern type hints


This section covers two connected things:

  A) Modern type-hint syntax:  dict | None ,  list[int] ,  dict[str, int]
  B) The line  from __future__ import annotations   , which lets you use the modern syntax on older Python versions.

They are grouped together because they solve the same problem: writing shorter, cleaner type hints.


1. THE OLD WAY vs THE MODERN WAY

Before you had to import helpers from the  typing  module. Now Python's builtin types can carry the hint directly.

Union (either type A or type B):

    # OLD  (needs:  from typing import Optional, Union )
    def find_user(user_id: int) -> Optional[str]:
        ...
    def parse(x: Union[int, str]) -> None:
        ...

    # MODERN  (Python 3.10+)
    def find_user(user_id: int) -> str | None:
        ...
    def parse(x: int | str) -> None:
        ...

Container types (list of ints, dict of str -> int, etc.):

    # OLD  (needs:  from typing import List, Dict, Tuple )
    def totals() -> Dict[str, int]:
        ...
    def names() -> List[str]:
        ...

    # MODERN  (Python 3.9+)
    def totals() -> dict[str, int]:
        ...
    def names() -> list[str]:
        ...

Two clear wins: no extra import, and the syntax is closer to how you already read the code.

This is where the next tool comes in.


2. WHAT   from __future__ import annotations   DOES

Python has a special module called  __future__  . Importing "features" from it turns on newer behaviour in an older Python version. The specific feature  annotations  changes ONE rule about how type hints are handled:

    Normally: type hints are EVALUATED at the moment the function is defined.
    With this future import: type hints are stored as raw STRINGS and never evaluated at runtime.

Because they are just strings, Python does not care whether the syntax inside is  Optional[int]  or  int | None  or  list[str]  — it treats them all as text. This lets you write modern-looking hints in a file that still runs under older Python.

    from __future__ import annotations

    def find_user(user_id: int) -> str | None:      # works even on Python 3.9
        ...

Without that top line, the same file on Python 3.9 would fail with:

    TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'

because Python 3.9 tries to evaluate  str | None  as a real expression at definition time.

Rule to remember: put   from __future__ import annotations   at the top of the file, and you can safely use modern hint syntax without worrying which Python version the code will run on (as long as it is 3.7+).


4. A CONCRETE EXAMPLE

Save this as  hints_demo.py :

    from __future__ import annotations

    def build_settings(port: int = 8080,
                       tags: list[str] | None = None) -> dict[str, int | str]:
        if tags is None:
            tags = []
        return {"port": port, "first_tag": tags[0] if tags else "none"}

    print(build_settings(9000, ["a", "b"]))
    print(build_settings())

Run:

    python3 hints_demo.py

Output:

    {'port': 9000, 'first_tag': 'a'}
    {'port': 8080, 'first_tag': 'none'}

The type hints do nothing at runtime — they are just documentation and are read by tools (editors, mypy, pyright) to catch bugs. The program runs exactly the same with or without them.


5. GOTCHAS TO KNOW

  - Hints become strings. If some library reads your type hints at runtime (dataclasses, FastAPI, Pydantic — you have not learned these yet, just remember the fact), it may need to call  typing.get_type_hints(func)  to resolve them back into real types. Most modern libraries handle this correctly on their own.

  - The  __future__  import only affects the CURRENT file. Every file that wants the modern syntax needs its own  from __future__ import annotations  line at the top.

  - This import must be the FIRST import in the file (after any module docstring and comments). It is a syntax rule; putting it lower can cause a SyntaxError.


6. COMMON MISTAKES

  - Using  int | None  in Python 3.9 without the future import. Fails at file-load time. Fix: add   from __future__ import annotations   at the top.

  - Forgetting the future import when you also use  list[int]  in a variable annotation (not a function signature). Same story — needs Python 3.9+ or the future import.

  - Mixing old and new styles in the same project. Not broken, just ugly. Pick modern-only (with the future import) and stick to it.

  - Assuming type hints are enforced at runtime. They are NOT. Python does not check them; you can pass a string to a function that expects  int  and Python will not complain. External tools (mypy, pyright) do the checking as a separate step.

  - Putting  from __future__ import annotations   BELOW a normal import. SyntaxError. It must be the very first import in the file (module docstring is allowed above it).
