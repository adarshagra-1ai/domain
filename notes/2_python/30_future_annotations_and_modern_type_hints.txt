30  --   from __future__ import annotations   and modern type hints

Section 17 introduced the modern hint forms  --   int | None ,  list[str] ,  dict[str, int] . This section covers the version problem that comes with them, and the one line that solves it.

1)  Which Python version each form needs

Section 17 showed both the  typing  style and the modern style. The part that matters here is WHEN each one became legal:

     Optional[str] ,  Union[int, str]        any Python 3.x, but needs  from typing import ...
     Dict[str, int] ,  List[str]             any Python 3.x, but needs  from typing import ...
     dict[str, int] ,  list[str]             Python 3.9 and up
     str | None ,  int | str                 Python 3.10 and up

So a file written with  str | None  simply fails to load on Python 3.9. That is the problem the next section solves.

2)  What  from __future__ import annotations  does

Python has a special module called  __future__ . Importing "features" from it turns on newer behaviour in an older Python version. The feature named  annotations  changes ONE rule about how type hints are handled:

     Without it:  type hints are EVALUATED at the moment the function is defined.
     With it:     type hints are stored as raw STRINGS and never evaluated at runtime.

Because they are just strings, Python does not care whether the text inside is  Optional[int]  or  int | None  or  list[str] . This lets you write modern-looking hints in a file that still runs under an older Python.

     from __future__ import annotations

     def find_user(user_id: int) -> str | None:
         ...

That works even on Python 3.9. Without the top line, the same file on Python 3.9 fails with:

     TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'

because Python 3.9 tries to evaluate  str | None  as a real expression at definition time.

Rule to remember: put  from __future__ import annotations  at the top of the file, and you can use modern hint syntax without worrying which Python version the code will run on (as long as it is 3.7+).

3)  A concrete example

Save this as  programs/hints_demo.py :

     from __future__ import annotations

     def build_settings(port: int = 8080,
                        tags: list[str] | None = None) -> dict[str, int | str]:
         if tags is None:
             tags = []
         return {"port": port, "first_tag": tags[0] if tags else "none"}

     print(build_settings(9000, ["a", "b"]))
     print(build_settings())

Run:

     python3 hints_demo.py

Output:

     {'port': 9000, 'first_tag': 'a'}
     {'port': 8080, 'first_tag': 'none'}

The type hints do nothing at runtime. The program runs exactly the same with or without them.

4)  Gotchas to know

  -  Hints become strings. If some library reads your type hints at runtime (dataclasses, FastAPI, Pydantic  --  you have not learned these yet, just remember the fact), it may need to call  typing.get_type_hints(func)  to resolve them back into real types. Modern libraries handle this on their own.

  -  The  __future__  import only affects the CURRENT file. Every file that wants the modern syntax needs its own  from __future__ import annotations  line at the top.

  -  This import must be the FIRST import in the file, after any module docstring and comments. It is a syntax rule; putting it lower causes a  SyntaxError .

5)  Common mistakes

  -  Using  int | None  in Python 3.9 without the future import. Fails at file-load time. Fix: add  from __future__ import annotations  at the top.

  -  Forgetting the future import when you use  list[int]  in a VARIABLE annotation rather than a function signature. Same story  --  needs Python 3.9+ or the future import.

  -  Mixing old and new styles in the same project. Not broken, just inconsistent. Pick modern-only (with the future import) and stick to it.

  -  Assuming type hints are enforced at runtime. They are NOT (section 17). You can pass a string to a function that expects  int  and Python will not complain. External tools ( mypy ,  pyright ) do the checking as a separate step.

  -  Putting  from __future__ import annotations  BELOW a normal import. That is a  SyntaxError . It must be the very first import in the file; only a module docstring is allowed above it.
