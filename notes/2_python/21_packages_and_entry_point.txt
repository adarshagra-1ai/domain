21  --  Packages and the program entry point  ( __init__.py  and  __main__.py )

Two special file names give a Python package its shape:

  -   __init__.py   --  the file that turns a plain folder into a PACKAGE.
  -   __main__.py   --  the file Python looks for when you run a package with  python -m .

1)   __init__.py   --  the package marker

 __init__.py  is a special file name in Python. Any folder that contains a file with EXACTLY this name (two underscores, "init", two underscores, dot py) becomes a PACKAGE  --  a folder that Python is willing to  import  as a single unit.

Without  __init__.py , the folder is just an ordinary folder on the disk. Python will not treat it as a package for a normal application.

The name "init" is short for "initialization". The code inside  __init__.py  runs ONCE, the very first time anything imports that package.

2)  What  __init__.py  can contain

Two common shapes:

  (a)  Empty (or almost empty). The file exists just to signal "this folder is a package". No real code  --  the mere presence is the message.

  (b)  Package setup code. Things like re-exports (making handy names from sub-files importable directly at the package level), a version string, or a config value.

3)  Example  --  an almost-empty  __init__.py

File:   src/mypackage/__init__.py

Whole file:

     """My package."""

Just a DOCSTRING (a triple-quoted string at the top of a file that Python treats as human-readable documentation for the module). No code beneath it. The file exists purely to tell Python "yes, treat  mypackage/  as a package".

4)  Example  --  an  __init__.py  that does work

File:   src/mypackage/__init__.py

Whole file:

     """My package  --  main engine."""
     from .clock import RealClock, SimulatedClock
     from .core import Engine
     from .runtime import State

     ENGINE_VERSION = "0.1.0"

     __all__ = ["Engine", "State", "RealClock", "SimulatedClock", "ENGINE_VERSION"]

Piece by piece:

  -  Top DOCSTRING  --  describes the package.

  -   from .clock import ...   --  the leading dot means "the current package". "The current package" is the folder where THIS file ( __init__.py ) sits. So  .clock  points at the file  clock.py  in that same folder  --  a SIBLING of  __init__.py .

     Folder view:

         src/mypackage/
             __init__.py    <-- this file
             clock.py       <-- ".clock"
             core.py        <-- ".core"
             runtime.py     <-- ".runtime"
             ... (more files)

     So the whole line reads: "from  clock.py  sitting right next to me, grab  RealClock  and  SimulatedClock  and pull them up to the package level (so outside code can  import  them straight from  mypackage )".

  -   from .core import Engine  and  from .runtime import State   --  same idea, applied to  core.py  and  runtime.py .

  -   ENGINE_VERSION = "0.1.0"   --  a plain package-level constant, so outside code can read  mypackage.ENGINE_VERSION .

  -   __all__   --  an explicit whitelist of the names the package makes public. Any name not in this list is treated as internal to the package.

5)  Why bother with the re-exports

Because outside code can now write the SHORT form:

     from mypackage import Engine, RealClock

instead of the LONG form:

     from mypackage.core import Engine
     from mypackage.clock import RealClock

The package hides its internal file layout and exposes only a clean set of public names. If tomorrow the developer moves  Engine  from  core.py  into a different file, outside code does NOT break  --  only  __init__.py  needs the update.

6)  What if  __init__.py  is missing

In a normal Python application, the  import  would fail with something like "No module named mypackage". A folder is not a package until  __init__.py  is there. So every package folder ships one.

7)   __main__.py   --  the entry point for  python -m

An ENTRY POINT is the first piece of code that runs when you launch a program from the command line. Every runnable program has one. The rest of the code is reached from the entry point onwards.

Python offers a few different ways to give a program an entry point. One common convention is the  __main__.py  file.

The name is not a developer's preference  --  it is the name Python HARD-CODES as the entry-point file for a package. Rename it to  run.py  or  start.py  and  python -m mypackage  will fail. Any other name needs a different launch style, such as running the file directly with  python somefile.py , which brings the import problems shown in section 9.

8)  How Python starts a program from the command line

Two common shapes:

  (a)   python somefile.py

        Python runs the code inside that ONE file. The file does not need to belong to any package. Simple, but the internal import paths can get messy.

  (b)   python -m somepackage

        The  -m  flag runs a MODULE as a script (section 14). For a PACKAGE, Python looks INSIDE it for a file named EXACTLY  __main__.py . If that file is present, Python runs it. If it is not present, Python prints an error and stops:

           No module named somepackage.__main__ ; 'somepackage' is a package and cannot be directly executed.

Example:

If a package lives inside  src/mypackage/ , running it from the command line looks like:

     python -m mypackage

Python finds  src/mypackage/__main__.py  and runs the  main()  function inside it. That function parses the command-line arguments, creates the main objects, and starts the program.

9)  Why prefer  python -m package  over  python file.py

Two reasons:

  (a)  Imports work naturally.

       Look at  __main__.py . Its first real code:

           from .clock import RealClock
           from .core import Engine

       The leading dot in  .clock  means "the current package". Python needs to KNOW which package that is, otherwise the dot has nothing to resolve against.

       Case A. Run with  -m :

           python -m mypackage

       Python is told up front: "the package we are running is  mypackage ". So when it hits  .clock , it knows  .clock  =  mypackage.clock  and finds  clock.py  in the same folder.

       Case B. Run the file directly:

           python src/mypackage/__main__.py

       Python sees only ONE file and treats it as a plain script  --  no package context at all. There is no "current package" to resolve  .clock  against, so the import fails with:

           ImportError: attempted relative import with no known parent package

       So the  -m  form is not just a nicer command  --  it is what LETS the package's own internal dotted imports resolve at all. Without it, they break outright.

  (b)  Cleaner user experience. The user does not need to know the internal file layout of the package. They type  python -m mypackage  and Python figures out where the entry file lives.
