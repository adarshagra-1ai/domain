23  --  argparse basics: ArgumentParser, add_argument, parse_args

This section covers argparse (the command-line parser we imported in section 22) in detail: creating a parser, registering flags of different shapes, and parsing the command line into an  args  object. We use a small  main()  function as the running example.

1)  The  main()  function signature

     def main() -> None:

The  def  keyword, the empty parameter list and the  -> None  return hint were covered in sections 12 and 17. What matters here is the NAME:  main  is chosen so the pattern  __main__.py -> main()  is easy to spot. When the entry guard at the bottom of the file calls  main() , execution starts here.

2)  What  main()  actually does

Two small words used below  --  SETTING and FLAG:

  -  SETTING  --  a value that controls how the program behaves, without changing the code itself. Examples: which folder to save data in, which port the API (Application Programming Interface) listens on, which network interface to bind to.

  -  FLAG  --  the way the user gives a setting on the command line. A flag starts with two dashes (like  --verbose ). Two shapes exist:

       -  flags with a VALUE after them  --  for example  --port 8000  or  --data-dir ./data ;
       -  on/off flags  --  for example  --verbose , which takes no value; its presence alone means "yes, turn this on".

Just two jobs:

  (a)  READ THE SETTINGS. Look at the flags the user typed on the command line (using argparse) and put them into an  args  object.
  (b)  PASS EVERYTHING TO  _run() . Call  asyncio.run(_run(...))  and send those values along.  _run()  is where the real work starts.

That is all.  main()  itself does no real work. It just prepares things and hands them off.

3)  Why  main()  is needed

Two reasons:

  (a)   python -m mypackage  needs a callable at the bottom of the file. The final two lines are literally  if __name__ == "__main__": main() , so Python needs a  main  function to call. Without it, running the module would do nothing.
  (b)  Async code cannot run on its own. Something has to wrap the async function with  asyncio.run(...) , which is a plain synchronous call.  main()  is that synchronous wrapper.

4)  What a PARSER is

A PARSER is a piece of code that reads raw TEXT and turns it into STRUCTURED DATA the rest of the program can use. The word "parse" just means "analyse and break apart".

Everyday examples:

  -  A JSON parser reads text like  {"a": 1, "b": 2}  and turns it into a real Python dict.
  -  A date parser reads text like  "2026-08-31"  and turns it into a Date object with year 2026, month 8, day 31.
  -  A URL (Uniform Resource Locator) parser reads text like  https://example.com/api?x=1  and splits it into scheme  https , host  example.com , path  /api , and query  x=1 .

argparse is a COMMAND-LINE parser. It reads the raw text the user typed on the shell after the program name  --  for example

     --data-dir ./data --verbose

--  and turns it into a Python object where each flag becomes an attribute:

     args.data_dir == "./data"
     args.verbose  == True

Without a parser we would have to write our own code to split that string, spot each  --  flag, pair each flag with its value, convert strings to integers where needed, and handle bad input. That is a lot of work. argparse does it all for us.

5)  Creating the parser

     parser = argparse.ArgumentParser(prog="my-engine")

This single line creates a fresh ArgumentParser object and stores it in a variable named  parser . The new piece here:

  -   prog="my-engine"   --  sets the program name that argparse shows in help messages. The first line of  python -m mypackage --help  will say "usage: my-engine ...".

The variable name  parser  is the developer's choice; it could have been  p  or  cli_parser . After this line runs,  parser  holds an EMPTY ArgumentParser  --  no flags added yet.

6)  Adding the first flag  (with a default value)

     parser.add_argument("--data-dir", default="./data")

 add_argument  is the method that registers one new flag on the parser. Its pieces:

  -   "--data-dir"   --  the FIRST argument, a plain string. This is the exact text the user has to type on the shell to set this flag.
  -   default="./data"   --  if the user does NOT type  --data-dir , argparse pretends the user passed  "./data" .

If the user types

     python -m mypackage

with no flags, then

     args.data_dir == "./data"

If the user types

     python -m mypackage --data-dir ./mydata

then

     args.data_dir == "./mydata"

Note the DASH-TO-UNDERSCORE rule: the flag name  --data-dir  turns into the attribute name  data_dir  on  args .

7)  Adding a flag without a default

     parser.add_argument("--config", help="path to a config JSON to import at start")

New piece:

  -   help="path to a config JSON to import at start"   --  sets the HELP TEXT for this flag. This text shows up when the user runs  python -m mypackage --help .

Notice: no  default=  is passed. So if the user does NOT pass  --config , then  args.config  comes out as  None .

     python -m mypackage                        ->  args.config == None
     python -m mypackage --config ./home.json   ->  args.config == "./home.json"

At this point  args.config  is just a STRING (the file path). The actual file is NOT opened here. That happens later, when the program uses that path to read the file.

8)  Built-in flags vs flags you define

Two categories exist:

  (a)  BUILT-IN, added automatically by argparse. You do NOT write  add_argument  for these. So far only two exist by default:

          -h  and  --help   --  show the auto-generated help output when the user runs  python -m mypackage --help . argparse builds this text from every flag that was registered via  add_argument , using each flag's own  help="..."  string.

  (b)  CUSTOM, added by the developer. Every flag in  main()  is one of these:  --data-dir ,  --config ,  --port ,  --bind ,  --verbose .

None of the custom names mean anything to argparse by default. They exist only because  main()  called  parser.add_argument  for each one. Try it: comment out any of those  add_argument  lines and pass that flag on the shell. argparse will reject it as "unrecognized arguments".

9)  Adding an integer flag  ( type=int )

     parser.add_argument("--port", type=int, default=8000,
                         help="HTTP API port (0 disables)")

Split across two lines only because it does not fit on one  --  the open parenthesis lets Python wrap. New piece:

  -   type=int   --  tells argparse to CONVERT the user's input from string to integer. If the user types  --port 9000 , argparse hands us the int  9000 , not the string  "9000" . If the user types  --port abc , argparse rejects it, because "abc" cannot be turned into an int.

 default=8000  is an integer here, matching  type=int .

10)  Adding a flag with multi-line help text

     parser.add_argument("--bind", default="127.0.0.1",
                         help="HTTP API bind address (dev surface, unauthenticated; "
                              "use 0.0.0.0 only on a trusted network)")

New piece  --  the help text is split across TWO adjacent string literals with no  +  in between:

     "HTTP API bind address (dev surface, unauthenticated; "
     "use 0.0.0.0 only on a trusted network)"

In Python, two string literals sitting next to each other in the source get JOINED into one string automatically. This is the common trick for wrapping a long help message across lines.

11)  Adding an on/off flag  ( action="store_true" )

     parser.add_argument("--verbose", action="store_true",
                         help="print debug information to the terminal "
                              "(useful for troubleshooting startup issues "
                              "and debugging misbehaving components)")

This one is an ON/OFF flag  --  a different shape from the four value flags above. New piece:

  -   action="store_true"   --  tells argparse: "this flag takes NO value on the shell. If it is PRESENT, set  args.verbose  to  True . If it is ABSENT, set it to  False ."

     python -m mypackage --verbose   ->  args.verbose == True
     python -m mypackage             ->  args.verbose == False

No  default=  is needed  --   store_true  already implies "default is  False ". The help text here uses the same string-literal joining trick, spread across three lines.

After this line, all FIVE flags are registered on the parser.

12)  Parsing the command line

     args = parser.parse_args()

This is the line where argparse ACTUALLY reads the command line the user typed and turns it into the  args  object. Up to this point nothing was read from the shell  --  we only DESCRIBED the flags. Now the reading happens.

 parse_args()  takes no arguments, because it already knows where to find the command line.

What happens inside  parse_args() , step by step:

  (a)  Read  sys.argv  (for example  ["--data-dir", "./mydata", "--verbose"] ).
  (b)  Walk through the tokens and MATCH each  --flag  against the registered flags. If a flag is not recognized, argparse prints an error and stops the program.
  (c)  For value flags (like  --port ), grab the next token as the value and CONVERT it to the declared type. If the conversion fails, argparse complains and stops.
  (d)  For on/off flags (like  --verbose ), set the attribute to  True  (present) or  False  (absent).
  (e)  For any flag the user OMITTED, fill in the  default=  value, or  None  if no default was declared.
  (f)  Wrap all those values into a single  argparse.Namespace  object and RETURN it.

That returned Namespace is assigned to  args . From this point on, every setting lives on  args  as an attribute:

     args.data_dir    # str,  "./mydata"
     args.config      # str or None
     args.port        # int,  8000 by default
     args.bind        # str,  "127.0.0.1" by default
     args.verbose     # bool, True or False

13)  What a NAMESPACE is

In general, a NAMESPACE is a container that holds NAMES and maps each name to a value.

Python has several kinds of namespaces:

  -  A MODULE is a namespace. The  math  module maps the name  pi  to  3.14159... , and the name  sqrt  to a function. Access with dot notation:  math.pi ,  math.sqrt(16) .
  -  A CLASS is a namespace. Names inside the class body (attributes, methods) are reached with dot notation on the instance.
  -  A FUNCTION has its own namespace while it runs  --  the local variables declared inside it (section 12, scope).

 argparse.Namespace  is a tiny CLASS inside the argparse module whose ONLY job is to act as an empty container. argparse fills it in with one attribute per parsed flag, and returns it. Attributes and dot notation are covered in section 16.

14)  Positional arguments  (no  --  prefix)

Every flag shown above starts with  --   --   --data-dir ,  --port ,  --verbose , and so on. Those are called OPTIONAL ARGUMENTS. Their trademark is the leading double dash and the fact that they can appear in any order on the shell.

argparse also supports a second shape: POSITIONAL ARGUMENTS. The name is registered WITHOUT any leading dash, and the user provides the value directly by POSITION on the command line  --  no flag name typed.

Simple sum example. Save this as  programs/sum.py :

     import argparse

     parser = argparse.ArgumentParser()
     parser.add_argument("a", type=int)
     parser.add_argument("b", type=int)
     args = parser.parse_args()

     result = args.a + args.b
     print(result)

Run it:

     $ python3 sum.py 2 3
     5

     $ python3 sum.py 10 25
     35

The new bits:

  -   "a"  and  "b"   --  the names have NO leading dashes. That is what makes them positional. The user does NOT type  --a  or  --b   --  just the values, in order.
  -  POSITION matters. The first value on the shell ( 2 ) goes into  args.a . The second value ( 3 ) goes into  args.b . Swap them and the result changes:  python3 sum.py 3 2  puts 3 into  args.a  and 2 into  args.b .
  -   type=int   --  without it,  args.a  would be the string  "2" , and  "2" + "3"  gives the string  "23" , not the number  5 .

Validation is automatic. Bad input gets rejected without any  try / except  in your code:

     $ python3 sum.py 2 hello
     usage: sum.py [-h] a b
     sum.py: error: argument b: invalid int value: 'hello'

Missing input is also caught:

     $ python3 sum.py 2
     usage: sum.py [-h] a b
     sum.py: error: the following arguments are required: b

15)  Positional vs optional  --  when to pick which

  -  Use POSITIONAL for values that are REQUIRED and have an obvious order. A sum program needs two numbers  --  nothing else makes sense.
  -  Use OPTIONAL ( --flag ) for values that are, well, optional, or when there are many settings and the user should not have to remember an order.

Both shapes can live on the same parser:

     parser.add_argument("a", type=int)
     parser.add_argument("b", type=int)
     parser.add_argument("--verbose", action="store_true")

     $ python3 sum.py 2 3 --verbose

Here  a  and  b  are positional,  --verbose  is optional. All three end up as attributes on  args :  args.a ,  args.b ,  args.verbose .
