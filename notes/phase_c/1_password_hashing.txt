C.1  --  Password hashing  (why, and the
         bcrypt idea)

1)  The problem  --  never store plain passwords

If you store user passwords as plain text
in your database:

  -  Anyone who reads the database (an
     attacker, a bad admin, a leaked
     backup) instantly knows every user's
     password.
  -  Users reuse passwords across sites,
     so the leak lets attackers into
     their email, bank, and every other
     account.

Rule: NEVER store plain passwords. Store
a HASH of the password instead. Your
database should only ever see the hash.


2)  What "hashing" is

A HASH FUNCTION takes an input (any
length) and returns a FIXED-LENGTH output
that looks random.

Two key properties:

  -  DETERMINISTIC. The same input always
     gives the same output.
  -  ONE-WAY. Given the output, you
     cannot get back the input (except by
     guessing).


Small example with SHA-256 (Secure Hash
Algorithm, 256-bit) from Python's
standard library:

Code:

     import hashlib

     h = hashlib.sha256(b"hello").hexdigest()
     print(h)

Output:

     2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

Every time you hash  b"hello"  you get
the same 64-character string. And there
is no easy way to reverse that string
back to  "hello" .


3)  Why plain hashing is not enough

Attackers precompute a big table:

     "123456"     ->  hash
     "password"   ->  hash
     "iloveyou"   ->  hash
     ...billions more...

When a stolen database of SHA-256 hashes
leaks, the attacker just LOOKS UP each
hash in the table. Millions of accounts
are cracked instantly.

Such tables are called RAINBOW TABLES.
Plain SHA-256, MD5 (Message Digest 5),
or SHA-1 is not safe for passwords.


4)  Salt  --  make every hash different

A SALT is a random string added to the
password BEFORE hashing.

     hash( salt + password )

Now the same password  "hello"  gives a
DIFFERENT hash for each user, because
each user has a different random salt. A
single rainbow table is useless: the
attacker would need one table per salt.

The salt is stored ALONGSIDE the hash in
the database (it does not have to be
secret; its only job is to be unique).


5)  Why bcrypt (not SHA-256)

Salting helps but is not enough on
modern hardware. A GPU (Graphics
Processing Unit) can compute BILLIONS of
SHA-256 hashes per second. Even with a
salt, brute-forcing short or common
passwords is quick.

Password hashing needs to be SLOW ON
PURPOSE.

bcrypt is a password-hashing algorithm
designed exactly for this. Its
properties:

  -  BUILT-IN SALT, generated for you and
     included in the output string.
  -  A COST FACTOR (number of rounds)
     that controls how slow the hash is.
     Higher cost = slower = harder to
     brute-force. You raise this over the
     years as computers get faster.
  -  Battle-tested: from 1999, still
     recommended today.

Alternatives with the same goals:
scrypt ,  argon2 . For our project we
use  bcrypt .


6)  Using bcrypt in Python

Install (inside your venv):

     pip install bcrypt


Hash a password:

Code:

     import bcrypt

     password = "hunter2"

     hashed = bcrypt.hashpw(
         password.encode(),
         bcrypt.gensalt(),
     )
     print(hashed)

Output (example):

     b'$2b$12$KIX...long...random...string...'

Notes:

  -  bcrypt works on BYTES, not str. Use
     .encode()  to convert.
  -  bcrypt.gensalt()  generates a fresh
     random salt. Default cost is 12.
  -  The output is BYTES. Store it in the
     database as text with  .decode() ,
     or keep it as bytes if the driver
     allows.


Verify a password:

Code:

     import bcrypt

     stored = b'$2b$12$KIX...long...string...'
     tried  = "hunter2"

     ok = bcrypt.checkpw(tried.encode(), stored)
     print(ok)

Output:

     True

bcrypt.checkpw  hashes the trial
password using the SALT stored inside
stored , then compares. You do not deal
with the salt yourself.


Adjust the cost:

Code:

     bcrypt.gensalt(rounds=14)

Higher rounds mean slower hashing.
Common values are 10 to 14. Test on your
target hardware.


7)  Where the hash lives in the database

Add a  password_hash  column to your
users table:

     CREATE TABLE users (
         id INTEGER PRIMARY KEY AUTOINCREMENT,
         email TEXT UNIQUE NOT NULL,
         password_hash TEXT NOT NULL,
         created_at TEXT DEFAULT
             (datetime('now'))
     );

The plain password never touches the
database. Only the bcrypt hash string
does.


8)  Full signup + login flow

Signup (server side):

Code:

     import bcrypt
     import sqlite3

     def signup(email, password):
         hashed = bcrypt.hashpw(
             password.encode(),
             bcrypt.gensalt(),
         ).decode()

         with sqlite3.connect("app.sqlite") as conn:
             conn.execute(
                 "INSERT INTO users (email, password_hash) "
                 "VALUES (?, ?)",
                 (email, hashed),
             )


Login (server side):

Code:

     import bcrypt
     import sqlite3

     def login(email, password):
         with sqlite3.connect("app.sqlite") as conn:
             row = conn.execute(
                 "SELECT password_hash FROM users "
                 "WHERE email = ?",
                 (email,),
             ).fetchone()

         if row is None:
             return False

         stored_hash = row[0].encode()
         return bcrypt.checkpw(
             password.encode(),
             stored_hash,
         )

Note: return the same "wrong credentials"
error whether the user does not exist OR
the password is wrong. Do not leak WHICH
one was wrong  --  that helps attackers
enumerate valid emails.


9)  passlib  --  a higher-level wrapper

passlib  is a Python library that wraps
bcrypt (and other algorithms) with a
simpler interface. Some projects prefer
it.

     pip install "passlib[bcrypt]"

     from passlib.hash import bcrypt

     hashed = bcrypt.hash("hunter2")
     bcrypt.verify("hunter2", hashed)

Under the hood it uses the same bcrypt
algorithm. Pick either  bcrypt  or
passlib  --  both are fine.


10)  Common errors

  (a)   Hashing a str, not bytes

        Code:

           bcrypt.hashpw("hunter2", bcrypt.gensalt())

        Run:

           TypeError: Strings must be
           encoded before hashing

        Add  .encode() :

           bcrypt.hashpw("hunter2".encode(),
                         bcrypt.gensalt())


  (b)   Storing the salt in a separate
        column

        You do NOT need to. bcrypt embeds
        the salt inside the hash string.
        One column ( password_hash ) is
        enough.


  (c)   Comparing hashes with  ==

        Do NOT do this:

           if bcrypt.hashpw(tried.encode(), salt) == stored:
               ...

        It would work in principle, but
        always use  bcrypt.checkpw  --
        it uses constant-time comparison
        to avoid timing attacks.


  (d)   Using SHA-256 or MD5 for passwords

        These are FAST hashes designed
        for file checksums, not for
        password storage. For passwords
        always use  bcrypt  (or
        scrypt  /  argon2 ).
